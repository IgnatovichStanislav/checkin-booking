# Checkin Booking: PMS to PDS

## Goal and scope

Build a local .NET test stand that receives PMS bookings, registers stays and guests with a Police Department System (PDS), and tracks registration status. Keep booking rules, mappers, freshness, outbox and PDS logic broker-independent; keep Kafka code in its own project that exposes Kafka keys, offsets, acknowledgments, retries, dead letters and replay explicitly. Do not add a generic queue abstraction; forks replace the broker project.

Flow: hotel/PMS -> map booking -> broker -> save booking -> register stay/guests with fictional Police Department System (PDS) -> receive result -> expose status to hotel/API/React monitoring UI.

Stack: .NET, PostgreSQL (durable state/outbox), Redis (disposable cache), webhooks, React + TypeScript monitoring/test UI. Redis/UI are optional for the first broker example. Use Docker Desktop/local services. PDS is a simulator; this is not H10's real architecture or legal guidance.

Current workspace contains guidance/tooling, diagrams and evals, not an implemented booking application. The user removed Kafke_Booking/, Input_Schemas/, Outbox_Schemas/ and RabbitMQ_Booking/. Other brokers (e.g. RabbitMQ, Pub/Sub) are out of scope here and will be implemented in separate forks reusing the same booking rules, fixtures and scenario IDs. Output adapters (PMS POST, webhook, file export, GET) still need contracts.

## Freshness and durability

Use source createdAt/updatedAt in UTC; no numeric SourceVersion or revision ordering. receivedAt is diagnostic, never freshness. Stay dates are hotel-local date-only values. Document source timestamp precision/guarantees; UTC does not ensure uniqueness or monotonicity.

Atomically compare updatedAt per booking in PostgreSQL:

- First/newer snapshot: apply booking and insert outbox row in one transaction.
- Older: ignore; no booking/outbox effect.
- Equal, identical normalized business data: duplicate; no effect.
- Equal, conflicting data: record conflict and reconcile with authoritative source; surface unresolved conflicts. Never break ties arbitrarily or with event IDs.

Exclude eventId/receivedAt from business-data comparisons. Guard concurrent arrivals in the database. Acknowledge intake only after durable acceptance (Kafka broker confirmation for the Kafka path); commit consumer offset/ack only after DB commit. Test redelivery without duplicate effects; do not claim exactly-once delivery. Hand dead letters off durably before acknowledging failed work.

## PDS and status

Reservation status (e.g. confirmed/cancelled), guest check-in (pending/checkedIn after required checks), and PDS status are separate. PDS acceptance does not check a guest in.

Proposed PDS states: pending (queued), awaitingData (missing information), submitted (processing), registered (confirmed), rejected (correct data), retryPending (known temporary failure), unknown (uncertain outcome; reconcile before resubmitting), error (investigate). Names/contracts remain provisional.

Correlate PDS results with a stable registration request ID; retries must not duplicate registrations. Track PDS status independently of PMS timestamps; delayed/duplicate results must not regress completed registration. Resume when missing information arrives. Expose status/safe error reasons through API/UI. Define amendments/cancellation explicitly; deleting a local booking does not cancel PDS registration.

## Required scenarios

- All intake: first/duplicate/stale/conflicting/invalid snapshots and concurrent delivery.
- H10: same booking ID across hotels, property authorization, webhook retry, missing-event reconciliation.
- Salou VIP: POST retry after timeout, unauthorized property.
- Cassis West: pagination, overlapping timestamp boundaries, interrupted polls and durable cursor recovery.
- Brokers: crash after DB commit/before ack, no duplicate booking/outbox effect, bounded retry and durable dead-letter handoff. Kafka: keyed ordering, offset commit after DB commit, replay from offset.
- PDS: success, missing data, rejection/correction, outage, uncertain timeout, duplicates, booking changes while pending.
